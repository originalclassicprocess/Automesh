# Пилотный запуск Automesh на automesh.space

Это инструкция для закрытого пилота, не заявление о готовности безопасного
мессенджера к массовому использованию. Версия 0.0.1 была запущена на хостинге;
следующий релиз и результаты проверки описаны в `CHANGELOG.md`.

Для ручного обновления одной кнопкой через GitHub Actions подготовлен отдельный
сценарий: [Обновления и откат](UPDATES.md). Сначала опубликовать актуальный код
и настроить SSH secrets; не запускать из старого состояния репозитория.

## Что запускается

Один Node-процесс обслуживает сайт и WebSocket `/signal`. Снаружи доступны
`https://automesh.space/` и `wss://automesh.space/signal` через HTTPS-прокси
хостинга. Сертификат домена обслуживает хостинг; локальный тестовый CA не нужен.
Не запускайте `vite dev`, `vite preview` или `npm run lan` на публичном сервере.

Страница, программа и иконки загружаются с сервера и сохраняются для PWA.
Сигналинг остаётся подключённым для поиска известных собеседников и согласования
соединений. Онлайн-сообщения/файлы идут по WebRTC. При включённом пересыльщике
сервер также передаёт зашифрованные конверты от домашней ноды получателю через WSS;
очередь хранится на ноде, не на публичном сервере. Сигналинг
видит Account ID, связи между ними и параметры соединений. Прокси хостинга может
вести собственные журналы IP, запросов и времени — отсутствие наших логов не
отключает журналы провайдера. Google STUN пока остаётся текущим интернет-дефолтом;
его можно заменить/отключить `MESH_RUNTIME_STUN_URLS`. LAN/QR его не используют.

## Что подтвердить у хостера ДО загрузки

- Node.js 22.12+ (лучше поддерживаемый LTS), запуск `app.cjs` как startup file.
- Передача WebSocket Upgrade на `/signal` через Passenger/HTTPS-прокси, без
  разрыва каждые несколько секунд. Наличие пункта Node.js в cPanel не гарантирует это.
- Только **один процесс/worker** приложения. Несколько изолированных процессов
  разделят пользователей между независимыми реестрами, и они не найдут друг друга.
- Процесс не должен засыпать/перезапускаться настолько часто, что постоянная
  связь не работает. Допустимый лимит постоянных соединений и трафика уточняется
  отдельно от дисковой квоты. Если хостинг этого не умеет, статический сайт можно
  оставить здесь, а сигналинг разместить на небольшом VPS с отдельным WSS-адресом.
- Фиксированный канонический HTTPS-домен, права на изменение заголовков/кэша,
  возможность отключить кэширование HTML, service worker и version.json в прокси.

1 ГБ RAM и 20 ГБ диска подходят для пилота, но не означают «любое число людей».
По умолчанию сервер допускает 256 живых WebSocket-соединений **с учётом** ещё
не зарегистрированных. Это защитный предел, а не измеренная ёмкость. База данных
для текущей модели не нужна. TURN пока отсутствует: сложные NAT, VPN и запреты
WebRTC могут помешать связи между отдельными сетями. Нельзя обещать доставку всем
пользователям интернета до соответствующих испытаний/добавления TURN.

## Подготовка локально

```sh
npm ci
npm run check
npm test
npm run release
node scripts/test-pwa-shell.mjs
npm run test:production
```

`.release/automesh-<номер>/` — отдельный пакет: `build/`, сервер, небольшой набор
общих JS-модулей, startup file, production-зависимости/lockfile, инструкция,
пример окружения и manifest с SHA-256 файлов. Node_modules не копируются.
Не загружайте весь рабочий каталог, `.git`, `.local-certs`, `.env`, резервные
копии аккаунтов, npm cache, исходные тесты или данные профиля браузера.
Manifest позволяет проверить целостность файлов, но **не является подписью**
и не защищает от злоумышленника, который может подменить и пакет, и manifest.

Тест серверной сборки локально в PowerShell:

```powershell
$env:NODE_ENV='production'
$env:ORIGIN='http://localhost:8080'
$env:PORT='8080'
npm start
```

HTTP разрешён только для localhost. Это отдельный тестовый origin, существующие
архивы `localhost:5173` он не переносит и не удаляет. Для обычных текущих тестов
LAN остаётся `npm run lan:pwa -- <IP ПК>`; все функции используют ту же сборку.

## cPanel (после подтверждения возможностей)

1. Создать Node-приложение вне `public_html`, связать с корнем automesh.space.
2. Загрузить содержимое подготовленного пакета в его application root.
3. Выбрать Node 22.12+ и startup file `app.cjs`, production-режим.
4. В окружении указать `NODE_ENV=production`, `ORIGIN=https://automesh.space`.
   `HOST=127.0.0.1`; порт задаёт Passenger — его PORT не заменять вручную.
5. Установить production-зависимости: `npm ci --omit=dev --ignore-scripts`.
   Сборка выполнена локально, компилятор на хостинге не нужен.
6. Перезапустить приложение средствами cPanel. Если на данном хостинге startup
   file должен называться иначе, изменить настройку, не переписывать программу
   под случайный порт. Порядок/поля панели зависят от установленного Node selector.

Приложение принимает GET/HEAD; отдельный `/api/device-pair/*` принимает только
ограниченные same-origin JSON POST для временного зашифрованного обмена заявкой
устройства. Сид/пароли/текст чата туда не передаются. Сессии хранятся только в
памяти до 10 минут, поэтому перезапуск/несколько worker прервут подключение.
Это не нода отложенных сообщений. `/dev` закрыт даже с поддельным Host.
Регистрация Account ID требует подписи одноразового вызова; тестовые `peer-*`
в публичном запуске запрещены. Действуют ограничения размера, частоты запросов,
числа наблюдаемых адресов и очереди сокета. Это не полноценная защита от DDoS:
лимиты TCP/HTTP и общий поток атак должны ограничиваться также прокси хостинга.
Произвольный `X-Forwarded-For` не считается доверенным источником IP.

## Кэш, обновление и откат

- HTML `/`, `/service-worker.js`, `/_app/version.json`: `Cache-Control: no-store`.
  Хешированные `/_app/immutable/*` допускают долгий кэш. Прокси/CDN не должны
  переписывать эти правила, HTML или JS; автоматическую оптимизацию JS выключить.
- Version ID детерминирован по исходникам/зависимостям: неизменённая сборка
  не создаёт лишнее обновление, изменённая получает новый ID. Можно задать
  собственный релизный `MESH_APP_VERSION` (новое значение на изменённый релиз).
  Worker проверяет совпадение версии
  HTML с собственным набором ресурсов, прежде чем считать установку успешной.
- Настройки → Приложение → «Проверить обновления» скачивает/проверяет полную
  копию, но не обновляет открытые вкладки. «Обновить приложение» сохраняет и
  блокирует доверенный аккаунт, затем перезагружает **только эту вкладку**.
  Временная недоверенная история требует отдельного согласия на потерю или
  предварительного перехода в доверенный режим. Черновики, активные передачи,
  незавершённые операции и ошибки сохранения блокируют обновление.
- Кнопка не стирает IndexedDB, сейф, контакты, медиа или весь кэш браузера.
  Старые версии кэша сохраняются, пока открытые клиенты используют их; если
  клиент не отвечает на запрос версии, очистка консервативно откладывается.
- Выкладка должна быть атомарной: подготовить отдельный каталог релиза с
  зависимостями, проверить, затем переключить application root/символическую
  ссылку средствами хостинга и перезапустить один процесс. Не заменять HTML,
  worker и набор модулей кусками на работающем приложении.
- Сохранить предыдущий релиз целиком. Старые хешированные клиентские ресурсы
  должны оставаться доступны через прокси/статический каталог при обновлении
  (новый клиентский каталог может дополнительно содержать старые immutable-файлы).
  Это нужно вкладкам, ещё не сохранившим полную старую офлайн-копию. Удалять
  старые файлы после периода обновления, а не при каждом деплое.
- Откат: вернуть предыдущий целый каталог и перезапустить процесс. Браузеры
  применяют возвращённую версию через ту же кнопку; не удалять пользовательские
  базы ради отката. При будущих несовместимых миграциях сначала нужна отдельная
  стратегия — текущая подготовка не меняет форматы аккаунта/архива/протокола.

CSP ограничивает исполнение скриптов своим origin/nonce, запрещает плагины,
встраивание страницы и внешние базовые URL; изображения/медиа допускают локальные
blob/data. Для пользовательских домашних узлов разрешены WSS-адреса в
`connect-src`; это осознанно шире одного домена, но клиент не сканирует сеть и
подключается только к одобренным адресам. CSP снижает риск некоторых XSS,
не защищает от подмены исходного сайта владельцем/взломщиком сервера, вредного
расширения, взломанного устройства или зависимости с вредоносным кодом.

## Приёмка после выкладки

### Обновление 0.0.1 → 0.0.2 через cPanel

1. До изменений сохранить копию текущего `build/` на хостинге и предыдущий
   ZIP. Сохранить также исходные настройки Node-приложения. Не удалять
   `node_modules`, `nodevenv`, сертификаты, `.env` или настройки cPanel.
2. Подготовить новый пакет локально с сохранением старых клиентских ресурсов:
   `npm run release -- --previous-release .release/automesh-<номер предыдущего релиза>`.
   Предыдущий каталог остаётся нетронутым; копируются только его хешированные
   ресурсы, а не старый HTML, worker или сервер.
3. Для простой выкладки остановить приложение кнопкой Stop App, распаковать
   содержимое нового ZIP непосредственно в application root (`automesh`),
   с заменой файлов. Не создать лишнюю вложенную папку `automesh/automesh-*`.
   На время обновления сайт/сигналинг будут недоступны. Альтернатива без
   частичной замены работающей сборки — отдельный каталог и атомарное переключение.
4. Зависимости в 0.0.2 не менялись: существующую установку npm сохраняем.
   Запустить приложение средствами cPanel. Домен, startup file `app.cjs`
   и переменные окружения остаются прежними.
5. Проверить `/_app/version.json`: строка начинается с `v0.0.2-`.
   В работающем клиенте применить обновление через Настройки → Приложение.
   Если аккаунт на iPhone ещё не создаётся, закрыть вкладку и открыть сайт
   заново; не стирать хранилище браузера ради обновления.
6. На iPhone проверить создание, восстановление из прежнего `.automesh`
   файла, блокировку/разблокировку и обмен сообщениями. Для неправильного
   пароля/изменённого файла восстановление должно по-прежнему отклоняться.

Новая версия не переносит аккаунты в другое хранилище: origin тот же.
Локальная история на другом устройстве автоматически не появляется.
При проблеме остановить приложение, вернуть предыдущую сборку и запустить
его снова; не удалять сейф/переписку пользователей.

### Общий чеклист

- `/healthz` возвращает только статус/версию протокола, `/dev` — 404.
- HTTPS без предупреждений, WSS `/signal` действительно работает, чужой Origin
  отклоняется. В HTML нет LAN-IP разработчика и локальных путей.
- Два независимых профиля/устройства создают аккаунты, принимают запрос,
  доставляют текст/файл и правильно подтверждают прочтение.
- Проверка на **разных** сетях (мобильная связь ↔ домашний Wi-Fi), не только LAN.
  Если нет ICE-пары, фиксировать ограничение и планировать TURN, не ослаблять
  проверку шифрования. Часть браузеров блокирует публикацию ICE-кандидатов.
- Проверить PWA после закрытия/запуска без сайта, восстановление по файлу,
  trusted/untrusted режимы. Кэш программы и доступность транспорта независимы.
- Две вкладки старой версии → новый релиз → явное обновление одной: вторая
  не перезагружается, история первой доступна после разблокировки. Ошибка
  загрузки/несовпадение версий не уничтожает последнюю рабочую копию.
- Откат на предыдущий релиз. Наблюдать только агрегированную нагрузку/ошибки,
  не включать журнал SDP/ICE/Account ID/содержимого сообщений.
- Обновлять зависимости осознанно с повтором check/test/build; не применять
  `npm audit fix --force` вслепую. Независимый аудит MAE v1 всё ещё не проведён.
  Известная проблема `cookie <0.7.0` закрыта совместимым override 0.7.2;
  сборка и интеграционные проверки выполнены с этим исправлением.

Справочные первичные источники: [SvelteKit adapter-node](https://svelte.dev/docs/kit/adapter-node),
[cPanel Node.js](https://docs.cpanel.net/knowledge-base/web-services/how-to-install-a-node.js-application/).
