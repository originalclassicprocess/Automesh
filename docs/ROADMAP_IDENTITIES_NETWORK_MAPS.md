# Automesh: связка профилей, доставка и карты

Дата: 2026-10-04. Статус: проект реализации для обсуждения, не описание уже
выпущенных функций. Этот документ не меняет приложение, доверие к сертификатам,
брандмауэр или сервер. Сроки и номера будущих релизов пока не назначены.

## 1. Цели и границы

- Сохранить действующие Account ID, восстановление, историю, подписи и E2EE.
- Добавить несколько профилей с одной резервной фразой, не раскрывая связь
  между ними по умолчанию.
- Отделить идентичность от роли, узла, транспорта и пользовательского модуля.
- Добавить доставку сквозных зашифрованных пакетов через HTTPS/WSS:443.
- Подготовить отдельно управляемые входящие и исходящие узлы.
- Добавить браузерные карты, затем региональные офлайн-пакеты для PWA.
- Делать изолированные изменения с проверкой совместимости и возможностью отката.

Не входят в первый выпуск: гарантированная анонимность, маскировка, неотличимая
от веб-сёрфинга, новая схема восстановления после кражи главной seed,
неограниченный сетевой трафик, фоновая работа закрытой PWA, полноценная
офлайн-навигация с поиском адресов и автоматическая смена всех идентичностей.

## 2. Теория: пять разных сущностей

| Сущность | Содержимое | Чего она не должна делать |
| --- | --- | --- |
| Идентичность | Собственная пара ключей подписи, Account ID, версия получения ключа | Определять способ доставки или давать всем сервисам доступ к seed |
| Профиль | Идентичность, отображаемое имя, контакты, настройки и история | Автоматически раскрывать другие профили владельца |
| Узел | Собственный рабочий ключ, подписанное разрешение, ограниченный набор услуг | Получать главную seed или автоматически расшифровывать переписку |
| Пространство | Группа, страница, канал, набор картографических отметок | Обязательно становиться новым аккаунтом |
| Каталог сервисов | Декларативные адреса, поддержанные возможности и правила доступа | Загружать произвольный исполняемый код от неизвестного сервера |

Субличность — самостоятельная идентичность, а не копия закрытого ключа
основного аккаунта с другим именем. Общая главная фраза нужна только для
восстановления ключей. Номер профиля и версия алгоритма входят в получение ключа.

Уточнение требований: главный корень по умолчанию локальный, не сетевой адрес
всех профилей. Каждый внешний профиль псевдонимный; «Все входящие» собираются
локально, без пересылки на root ID. Публичная связка — только явное действие.
Совместимость старого аккаунта и границы анонимности: `PROFILES_PRIVACY_CONTRACT.md`.

«Карты» обычно являются модулем. Отдельный профиль «Карты» полезен, если человек
хочет публиковать отметки под отдельным псевдонимом; смотреть карту без него можно.

Каталог внутри интерфейса не равен DNS/name service. Он может показывать
проверенные шаблоны сервиса. Отображаемый ник не является доказательством личности:
доверие привязывается к ключу и Account ID. Глобальный поиск уникальных имён —
отдельный будущий протокол с конфликтами, подменой записей и доступностью каталога.

## 3. Связка и восстановление

### Получение ключей

- Старый профиль использует прежний `mesh/identity/v1` без изменения байтов.
- Новые используют отдельную версию схемы, фиксированный контекст, назначение и
  стабильный целочисленный индекс. Предлагаемый примитив — HKDF-SHA-256 с
  документированным кодированием контекста; это ещё не утверждённый формат.
- Проверить преобразование результата в допустимый скаляр P-256 и закрепить
  тестовые векторы. Не подменять этим схему Bitcoin BIP32: здесь другая кривая.
- Переименование, удаление или сортировка профиля не меняют индекс и ключ.
- Удалённые индексы по умолчанию не использовать повторно. Конкурирующее создание
  в двух вкладках/устройствах должно выявляться, а не создавать незаметные дубликаты.

Обоснование разделения контекстов: [HKDF, RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html).

### Состояние и резервная копия

Зашифрованный реестр связки хранит индексы, версии, имена, состояния профилей,
выбранный профиль, подключения сервисов и отметки удаления. Номера не являются
секретными ключами, но реестр раскрывает принадлежность аккаунтов одному человеку.

Новая резервная копия содержит фразу и этот реестр; отдельно предусматривается
копия истории и случайных ключей доставки. Старые файлы импорта продолжают
восстанавливать старый профиль. Полный бэкап данных — отдельный формат и интерфейс.

Фраза восстанавливает ключи при известном индексе/версии, но сама не хранит список
профилей, переписку, одноразовые ключи доставки или карты. Без реестра доступны
ручной выбор индекса и ограниченный перебор диапазона. Определить последний
созданный профиль или восстановить ник по одной фразе без дополнительных данных
нельзя обещать. Обычное восстановление не должно публиковать весь диапазон ID
серверу для проверки активности.

### Изоляция

- Утечка главной seed раскрывает все производные профили, в том числе будущие.
- Утечка только дочернего ключа не должна позволять вычислить остальные.
- Публичное подтверждение «этот профиль принадлежит этому владельцу» опционально:
  такая подпись раскрывает связь. Локальному реестру публичное подтверждение не нужно.
- Не держать все ключи постоянно разблокированными. Для «Всех входящих» явно
  выбирать, какие профили активировать, и показывать их статус.
- Профили в одном origin — логическая изоляция данных, не разные защищённые
  процессы. XSS/подменённая сборка может затронуть все открытые профили. Разделение
  ключей не устраняет доверие к коду клиента; для более сильной изоляции понадобится
  отдельный процесс/контейнер или другой проверенный механизм исполнения.
- Главный материал используется при открытии/создании профиля, временные буферы
  очищаются насколько позволяет JS; физическое стирание памяти не гарантируется.
- Независимые аккаунты оставить отдельным режимом. Их существующие случайные
  ключи нельзя просто вывести из другой seed; импорт требует отдельного хранения
  секретов в бэкапе, а не обещания восстановления одной фразой.

## 4. Сценарии интерфейса

- По умолчанию один личный профиль, без обязательных дополнительных настроек.
- Дополнительные шаблоны: «Работа», «Псевдоним», «Публичные публикации».
- «Все входящие» — представление раздельных историй, не пересылка на основной ID.
- У чата и поля ответа виден профиль отправителя. Ответ остаётся от адресованного
  профиля; смена отправителя требует явного действия.
- Профиль можно исключить из агрегированного просмотра, поиска и уведомлений.
- Один узел может исполнять обе почтовые роли, но права/очереди отображаются отдельно.
- В настройках: «Моя связка», «Доставка», «Карты», «Память».

## 5. Узлы и коннекторы

Общий контракт описывает возможности (`relay`, `mailbox`, `storage`, `map-pack`),
версию, ограничения, адрес и состояние подключения. Не пытаться сделать все
облака одним одинаковым API: WebDAV, файловый диск и Automesh-нода требуют своих
адаптеров авторизации, CORS и операций. Общие сценарии приложения используют
контракт, а не специфические запросы провайдеров.

Для узла предлагается подписанное профилем разрешение: ключ узла, профиль,
разрешённые действия, время действия, версия/эпоха и идентификатор разрешения.
Авторская подпись сообщения остаётся отдельной от подписи узла. Рабочий ключ
узла случайный; переустановка создаёт новый ключ и требует повторной привязки.

Отзыв действует после получения актуального состояния и/или истечения срока
разрешения. Мгновенный отзыв для полностью отключённого клиента невозможен.
Нужно определить распространение обновлений разрешений до их реализации.

Входящий узел хранит шифротекст для разрешённых профилей и отдаёт его после
проверки доступа. Для приёма из интернета узел устанавливает исходящую WSS-связь
с выбранным реле; домашние входящие порты не пробрасываются. Как реле направляет
пакеты к разрешённому входящему узлу — часть нового согласованного протокола.
Имеющаяся исходящая очередь не означает, что входящая роль уже реализована.

## 6. HTTPS/WSS-доставка

### Два разных режима

1. Автоматический: прямое соединение, при недоступности — веб-реле/очередь.
2. Только веб-реле: не создавать WebRTC/STUN/ICE для такого чата, включая входящие
   предложения. Иначе прямой IP может раскрыться ещё до перехода на резерв.

Не требуется маскировать UDP под HTTPS. Через WSS или HTTPS API передаются
действительно защищённые веб-соединением пакеты. Внутренние авторские подписи и
E2EE остаются, реле не получает ключи расшифровки. Это не обещание анонимности:
реле видит маршрутные метаданные, а сеть — конечный сервер, объёмы и время.

### Порядок реализации

- Выделить адресную доставку конвертов из сигналинга за внутренним интерфейсом.
  Для первого этапа тот же сервер/443 допустим, но очереди, квоты и типы сообщений
  должны быть разделены. Существующий courier-путь уже частично использует WSS.
- Онлайн-реле реализовать адаптером `Transport` с порядком пакетов, обратным
  давлением, проверкой получателя и ограничением неизвестных отправителей.
- Проверить аутентифицированный обмен E2EE-рукопожатиями через новый транспорт:
  сервер не должен подменять доверие к ключам или требовать открытого текста.
- Разделить транспортное принятие пакета, сохранение на узле, получение адресатом
  и прочтение. Подтверждение сервера не считать подтверждением адресата.
- Повторы идемпотентны; переключение пути не дублирует сообщения и не смешивает
  старую и новую сессию. Для смены криптосессии переупаковывается прикладное
  сообщение, а не бездумно переотправляется кадр старой сессии.
- После текста/ответов/контактов отдельно реализовать ограниченные части файлов,
  возобновление, квоты и проверку целостности. Не делать неограниченные WS-пакеты.
- Почтовая офлайн-доставка с одноразовыми ключами остаётся отдельным сценарием:
  наличие WSS не позволяет закрытой PWA постоянно принимать сообщения.

Смена идентичности ноды раз в сутки не стирает метаданные, не отменяет
компрометацию владельца и может ломать очередь. Сначала реализовать разрешения,
отзыв и перенос незавершённых задач, затем обсуждать ротацию.

## 7. Карты на iPhone и других устройствах

Предлагаемый прототип: лениво загружаемый MapLibre GL JS и региональный PMTiles.
Библиотека рисует карту в браузере; PMTiles имеет FileSource для выбранного
пользователем локального файла. Это техническая основа, а не подтверждение работы
на конкретном iPhone: производительность/хранение проверяются отдельным прототипом.
[MapLibre](https://maplibre.org/maplibre-gl-js/docs/),
[PMTiles FileSource](https://pmtiles.io/typedoc/classes/FileSource.html).

Первый режим: просмотр области, масштабирование, свои отметки, выбор точки для
отправки в чат. Разрешение геолокации запрашивается только по кнопке. Текущий
запрет геолокации в Permissions-Policy надо адресно изменить, если добавляется
«Моё местоположение»; для ручной точки GPS не нужен.

Офлайн-пакет включает тайлы, стиль, шрифты, значки, границы, диапазон масштабов,
версию, лицензию/атрибуцию и контрольные суммы. PMTiles сам по себе не гарантирует
наличие всех этих ресурсов. Проверка хэша из недоверенного пакета не доказывает
надёжность автора: для доверенных пакетов нужен известный источник/подпись.

- Импорт через выбор файла, а не запуск приложения по `file://`.
- Чтение диапазонов файла без загрузки всего архива в оперативную память.
- Постоянная копия в браузерное хранилище опциональна; после перезапуска выбранный
  файл может потребоваться выбрать снова. Не полагаться на desktop File System
  Access API на iPhone без проверки поддержки.
- Перед копированием оценивать объём/квоту; обрабатывать нехватку места, прерывание
  импорта и восстановление после закрытия. Запрашивать persistent storage, не
  обещая, что браузер обязательно предоставит его.
- Карты скачиваются/импортируются отдельно от основной PWA-сборки. Их удаление
  не удаляет аккаунты; обновление приложения не перескачивает весь регион.
- Хранить историю просмотров и личные отметки отдельно от публичной подложки;
  отметки шифровать. Выбор региона/запросы тайлов тоже чувствительны для приватности.
- Код/worker/стили библиотек поставлять в сборке, не через исполняемый CDN.
  Не отключать CSP ради карт. Импортированные стили не должны обращаться к
  произвольным сетевым адресам; содержимое всплывающих подсказок не исполнять как HTML.
- Онлайн-источник выбирается по условиям провайдера. Стандартный OSM tile-сервер
  запрещает массовую загрузку/офлайн-пакеты и требует Referer. Текущий
  `no-referrer` Automesh с таким источником несовместим; не ослаблять глобальную
  политику автоматически. Выбрать допустимый источник или собственные пакеты.

[Правила OSM](https://operations.osmfoundation.org/policies/tiles/).
Safari/PWA поддерживает локальное хранилище, но по умолчанию данные могут быть
вытеснены. Установка PWA не является резервной копией.
[Политика WebKit](https://webkit.org/blog/14403/updates-to-storage-policy/).

Офлайн-поиск адресов и построение маршрутов требуют дополнительных индексов,
данных и движка: они не появляются от загрузки картографической подложки.

## 8. Последовательность изолированных итераций

| Этап | Работы | Критерий перехода дальше |
| --- | --- | --- |
| A. Безопасность | План вывода старого CA, точечные firewall-правила, квоты по источнику/получателю, ограничение неизвестных WebRTC-пиров, HSTS | Не ломаются доверенная нода/LAN; перегрузка одного участника не блокирует остальных; старое доверие удаляется по явному согласованию |
| B. Контракты и миграции | Реестр профилей, формат бэкапа, профильный storage scope, версии возможностей транспорта | Старые Account ID/бэкапы совпадают с эталонами; миграция атомарна, ошибки не удаляют исходные данные |
| C. Профили | Создание/переключение, изолированные чаты, backup/restore, затем «Все входящие» | Тесты двух профилей, lock/unlock, двух вкладок, отказа записи; ответы не уходят от другого ID |
| D. Веб-реле | Новый транспорт с прежними подписанными E2EE-пакетами; ручной режим до автоматического fallback | Передача между разными сетями; дубликаты/подмена/повторы/обрыв не нарушают подписи и статусы; режим relay-only не создаёт ICE |
| E. Почтовые роли | Исходящая/входящая роли, ограниченные разрешения, отзыв, сохранение очереди и ключевые запасы | Доставка без отправителя, без открытого получателя через inbox, перезапуск ноды, исчерпание ключей и TTL без потери/ложного Delivered |
| F. Карты: прототип | Отдельная вкладка, разрешённый источник, локальный небольшой пакет | Реальные iPhone/Android/ПК: полётный режим, перезапуск PWA, подписи/иконки офлайн, измеренные память/размер/время |
| G. Карты: продукт | Импорт/удаление регионов, мини-дашборд, отметки, отправка точки | Нет скрытых внешних запросов офлайн; удаление карты не затрагивает vault; повреждённый файл отклоняется безопасно |
| H. Пространства | Страницы/каналы, затем отдельный проект шифрования групп | Согласованы публичность, роли, смена участников и последствия потери ключей; узел не считается доверенным читателем автоматически |

Этап F можно прототипировать независимо после A; публиковать только после
проверки ограничений устройства. Для изменений ноды D/E требуются новый
установщик и согласование возможностей со старыми клиентами. Профили/карты сами
по себе не требуют обновления установленной ноды, если её протокол не меняется.

Не удалять все лимиты: отделить квоты защиты от DoS, квоты хранения и количество
одноразовых ключей. По показанию «12 сообщений» сначала определить реальный
источник. Простое увеличение диска не создаёт новые ключи. Сделать пополнение
доступных ключей и объяснимое состояние; допустимый офлайн-запас требует отдельного
решения, а использованные приватные ключи нельзя хранить ради бесконечной очереди.

## 9. Проверки и публикация

- Эталонные ключи/ID старой версии и векторы новой; отрицательные тесты контекстов.
- Испорченный реестр, неверный пароль, частичная миграция, старая резервная копия.
- Изоляция профилей, ошибки переключения, конкурентные вкладки, блокировка во время
  доставки, сохранения и импорта. Секреты не появляются в логах/телеметрии.
- Локальный adversarial-тест сигналинга/ноды без нагрузки на production;
  привязка, Origin/Host, повтор proof, большие пакеты, подпись и неверный получатель.
- Доставка при ограниченном UDP, через выбранные реле, без открытого отправителя,
  после перезапуска; режим web-only с проверкой отсутствия STUN/ICE запросов.
- Картографические фикстуры: нет файла/шрифтов/места, повреждённый архив, huge metadata,
  внешний URL в стиле, закрытие вкладки, выгрузка WebGL-контекста и аварийное удаление.
- Проверка Chrome/Android, Safari/iPhone и Windows с конкретными версиями устройств.
  Автотесты не заменяют физический тест iPhone и независимый криптоаудит.
- Каждый этап — отдельный релиз, журнал миграции и совместимости. Не смешивать
  смену ключевого формата, транспорта и большие UI-изменения в одном выпуске.
- Откат бинарной версии не должен откатывать состояния одноразовых ключей или
  восстанавливать потреблённые секреты. Совместимость отката проверяется заранее;
  если её нет, используется восстановление/исправление вперёд с сохранением данных.

## 10. Решения перед реализацией

Рекомендуемые стартовые варианты:

1. Действующий аккаунт сохраняется как старый внешний профиль без смены ID;
   новый корень связки не публикуется. Для новых пользователей отдельный внешний
   личный профиль создаётся по умолчанию, не используя root ID для сети.
2. «Карты» сначала модуль без обязательной новой идентичности; отдельный профиль
   используется только для публикации/обмена отметками по желанию.
3. Связь между профилями приватная; публичная делегация нужна сервисам, которым
   владелец явно выдаёт полномочия, а не всему каталогу.
4. HTTPS/WSS сначала ручной web-only/relay-only режим для текстовых сообщений,
   затем автоматический переход; нет маркетингового обещания неотличимости от HTTPS.
5. Одна нода с двумя явно включаемыми ролями; разнести на две можно позже.
6. Карты сначала небольшой регион и ручной импорт; большой мир, поиск адресов,
   навигация и фоновое слежение не входят в первый этап.
7. Реальные лимиты/источник пакетов карт/распространение отзыва согласовать по
   измерениям и условиям эксплуатации, не выбирать случайные постоянные числа.
