# Связка профилей v1 — первая локальная итерация

Дата: 2026-10-04. Реализованы библиотека, управление в Настройки → Аккаунт,
совместимый зашифрованный файл связки и изолированный `/dev/profiles`.
Опубликовано в релизе 0.1.5 (`v0.1.5-d2a144217cb97b6e`). Реальные чаты ещё не переключаются между профилями, автоматическая
миграция сейфа не выполняется. Production закрывает тестовый экран.

## Сущности

- Корневой 32-байтный материал восстановления: только локальный секрет. Это
  существующий identitySeed, а не текст BIP-39 и не весь 64-байтный BIP-39 seed.
- Главный профиль «Все входящие»: отдельная производная идентичность с индексом 0.
  Не совпадает с корнем или старым аккаунтом. По умолчанию сетевой вход выключен;
  получение его подписанта требует отдельного явного выбора trusted host.
- Личный, Входящий, Исходящий, Другой: отдельные производные ключи/Account ID,
  назначение не входит в деривацию. Роль пока не меняет транспорт/поведение ноды.
- Старый аккаунт: один явный legacy-профиль с прежним ключом/ID, index=null.
  Инициализация проверяет соответствие корневого материала его ID; история
  не переносится автоматически и ни один прежний ID не заменяется.

Для нового реестра создаётся только главный профиль; остальные добавляет
контроллер. Тестовый пример добавляет legacy, входящий и исходящий для проверки.
Управление открывается повторным вводом пароля, закрывается при уходе в фон,
выходе из раздела и блокировке. Создание связки явно сохраняет прежний аккаунт
как личный. Импортировать прежнюю связку следует до новой инициализации.
Входящий/Исходящий создаются отдельными кнопками формы с выбором назначения.
Эти адреса пока не регистрируются в сети: настоящий чат остаётся прежним.

## Ключи

Схема `automesh-profile-hkdf-p256-v1`. HKDF-SHA-256:
salt=`Automesh profile identity v1`, info=UTF8(JSON.stringify([scheme,index,counter])),
32 байта результата. Индекс — uint32, counter начинается с 0. При недопустимом
скаляре P-256 повторяем с новым counter (до 128); не применяем смещающее modulo.
Фиксированные векторы индексов 0,1,2,2^32-1 сверены с Node hkdfSync.
Переименование/архивирование не меняет ключ, nextIndex только возрастает.
Входящий/исходящий адреса различаются между собой и с главным/legacy.

Главная seed компрометирует всю связку; один дочерний секрет не позволяет
обратить HKDF и получить корень/соседей. Это не новый механизм восстановления
после кражи seed. Физическое стирание JS-памяти не обещается.

## Два независимых направления подключения

1. `contribute`: главный видит входящие конкретного субпрофиля.
2. `read-all`: субпрофиль видит перечисленные источники общего ящика.

Запрос может начать любая из двух сторон. Начальная заявка фиксирует согласие
инициатора. Другой участник должен принять; повторное подтверждение инициатором
не проходит. Запрос действует 10 минут, разрешение не более 7 дней от создания.
Новый срок/набор источников требует нового подтверждения. Обе стороны могут
отозвать доступ. Архивирование отзывает активные/ожидающие подключения;
обратное включение не восстанавливает разрешение.

`read-all` фиксирует список подключённых источников на момент заявки.
Будущие профили/подключения не расширяют его. Отозванные/истёкшие источники
немедленно исключаются из разрешённой проекции. Главный видит только свои
входящие и явно подключённые источники, а не всё вопреки отказу субпрофиля.
Обычный субпрофиль всегда видит своё, но не чужое.

Подключение не даёт подписант, seed, право отвечать от чужого имени или право
запускать код. Ответы в будущем привязываются к исходному профилю чата.
Это локальная проекция данных, а не публикация реестра или отправка корню.
Прочитанное/скопированное ранее невозможно отозвать задним числом.

## Граница доверия (важно)

Пока это **локальные профили одной связки**, с согласием через доверенный
контроллер. Передаваемый actorId — контекст этого контроллера, не утверждение
неизвестного клиента. Dropdown тестового экрана демонстрирует стороны, а не
доказывает владение чужим аккаунтом. Все производные ключи подконтрольны владельцу
корня; такой интерфейс не изолирует его от самого себя или вредоносного клиента.

Подключение независимого аккаунта/другого устройства потребует отдельного
протокола: доказательство владения обеими идентичностями, подписанные запросы
с nonce/сроком, защита от повторов, E2EE-доставка содержимого, согласованное
состояние отзыва. Нельзя принимать произвольный actorId из сети как подтверждение.
HTTP API и удалённый аналог WalletConnect этим этапом не реализованы.

## Хранение и ограничения

Отдельная IndexedDB `automesh-private-profiles-v1`. Оболочка scope/revision/IV/cipher;
имена, индексы, адреса профилей и подключения внутри AES-GCM-256. HKDF ключа:
salt=`Automesh private profile registry v1`, info=scope. AAD связывает назначение,
scope и ревизию. Scope — локальный ID хранилища, не публичная связка.

CAS не перетирает конкурирующую запись, crypto вне коротких транзакций.
Случайный новый IV при каждом retry. Ключ неизвлекаемый. Реестр разрешён только
в доверенной сессии; нет запасного plaintext/memory-хранилища. Закрытие гасит
дочерние подписанты, guard эпохи не позволяет старой вкладке писать после сброса.
Экстренное стирание включает реестр. Обычная очистка истории его не удаляет.

Сохраняется верхняя отметка времени, в том числе при чтении: обычный перевод
часов назад не оживляет истёкшие права. Полный rollback/удаление базы, XSS и
подмена сборки не решаются этой моделью. Независимые устройства пока не
синхронизируют nextIndex: нельзя обещать глобальную уникальность создаваемых
профилей между несинхронизированными копиями связки.

Защита парсера: до 256 записей профилей, 128 записей заявок/разрешений,
64 KiB и сложность canonical JSON v1 (что может ограничить раньше числа записей).
Это инженерные пределы первого формата, не платный лимит или ограничение
математического числа ключей. Старые заявки не вытесняются молча; политика
очистки/журналирования — отдельная доработка.

Одна фраза восстанавливает производные ключи по известным индексам/версии,
не ник, список созданных профилей, заявки, историю и случайные ключи доставки.
Старый файл формата 1 реестр не содержит и остаётся читаемым. Новый формат 2
включает реестр в AES-GCM с отдельным version-bound AAD. PBKDF2-SHA256:
600000 итераций, случайные соль 16 байт и IV 12 байт — без ослабления защиты.
Максимальный файл 128 KiB, реестр по-прежнему до 64 KiB. Все дочерние адреса,
включая архивные, проверяются деривацией из seed при экспорте, открытии и импорте.
У файла нет открытого списка профилей. Имя файла по умолчанию без ника.

Верификация сохранённого файла сверяет не только seed/Account ID, но и полный
экспортированный снимок реестра: старый файл с той же seed не считается копией
новой связки. После изменения профилей копию нужно сделать заново. Бумажная
seed не сохраняет названия, список индексов, права и историю.

Восстановление файла 2 подключено к обычному входу из файла (с доверенным режимом),
а также к импорту внутри управления профилями. Импорт — добавочный:
совпадающие локальные имена/архивы/права не заменяются; nextIndex и lastNow
не уменьшаются. Конфликт UUID/индекса/адреса отклоняется, без подмены реестра.
В импортированной копии ВСЕ разрешения сбрасываются: их подтверждают заново.
Если локальный реестр уже есть, его текущие права остаются, старые из файла
не возвращаются. Запись реестра — CAS; сохранение самого сейфа и реестра не
является общей атомарной транзакцией между localStorage и IndexedDB.

Обычный экспорт в доверенной сессии включает существующий реестр; ошибка чтения
не заменяется незаметно файлом без профилей. В недоверенной сессии обычный
файл содержит только seed/ник, о чём есть предупреждение в интерфейсе.
Переписка, вложения, случайные ключи доставки и ожидающие конверты в этот бэкап
не входят. Перед сетевым переключением ещё нужны явная миграция и изоляция
истории/очередей каждого профиля.

## Проверка локального экрана

`npm run dev`, открыть http://127.0.0.1:5173/dev/profiles.
Создать тестовую связку → выбрать Входящий → запросить передачу → выбрать
Все входящие → принять и подтвердить. Только главный начинает видеть источник.
Запросить чтение общего ящика отдельно, подтвердить второй стороной. Отозвать.
Перезагрузить ту же ссылку с run=… → «Открыть сохранённую связку».
Все операции направлены в `automesh-profile-check-v1-<run>`, данные пользователя
и глобальная эпоха сброса не изменяются. Корневой ключ примера общеизвестен.

Проверено 2026-10-04 в настольном браузере: отдельные адреса, сохранение
после перезагрузки, подтверждение передачи другой стороной, отсутствие
автоматического обратного доступа, отдельное подтверждение чтения и его отзыв.
Проверка типов без ошибок/предупреждений; тесты приложения и сервера — 469/469.
Проверка на физических Android/iPhone на этом этапе не выполнялась.

## Проверка второго этапа (управление и бэкап)

В `/dev/profiles` нажать «Проверить окно управления профилями»; пароль
`public-test-password` относится только к общеизвестному тестовому аккаунту.
Создать связку, затем профили Входящий/Исходящий. Сохранить связку в файл,
скачать и выбрать её обратно для проверки. Скрытие окна/уход в фон закрывает
ключи; после повторного пароля открывается сохранённая связка. Тестовый
компонент использует отдельный scope в `automesh-profile-check-v1-<run>`.

В настольном браузере проверены открытие управления, создание прежнего личного
и двух новых профилей, подготовка файла с четырьмя профилями. Получить файл
для обратного выбора через встроенную автоматизацию не удалось (download
event недоступен/тайм-аут); полный UI download/upload требует обычного браузера.
Автотесты проверяют v1/v2, неправильный пароль, подмену версии/дочернего адреса,
снимок входных данных, импорт без возвращения старых прав, конфликты, CAS,
границы сессии и отсутствие silent seed-only fallback при повреждении реестра.
Полный прогон второго этапа: 489 тестов приложения/сервера.
