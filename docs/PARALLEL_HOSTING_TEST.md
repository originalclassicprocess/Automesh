# Две независимые установки для проверки связи

Состояние на 25 октября 2026 года:

| Адрес | Назначение | Версия |
|---|---|---|
| `https://automesh.space` | Старое приложение, оставлено для сравнения | 0.3.11 |
| `https://node.automesh.space` | Действующая старая нода; не перенесена | 0.4.5 |
| `https://automesh.online` | Новое приложение, обновлено через GitHub | 0.4.0 |
| `https://node.automesh.online` | Новая отдельная серверная нода | 0.4.5 |

DNS и программные файлы старой установки в этом этапе не менялись. Новая нода
имеет собственные master key, node ID, конфигурацию и очереди. Копирования старых
профилей/ключей/конвертов на неё не было.

## Первый вход администратора новой ноды

В Terminal НОВОГО cPanel выполнить:

```sh
"$HOME/nodevenv/automesh-node-app/24/bin/node" "$HOME/automesh-node-app/adapters/passenger/main.js" admin-setup "$HOME/.automesh-node-private/config.json"
```

Команда выдаст краткоживущий одноразовый код первоначального назначения
администратора. Не публиковать его в чате, GitHub, логах или скриншотах.
Ключи и очередь она заново не создаёт. Выполнять на новом хостинге; не на старом.

Открыть `https://node.automesh.online/`, выбрать вход через Automesh и подтвердить
его из своего профиля на `https://automesh.online`. Ввести первоначальный код
там, где приложение запросит код назначения администратора. Это не приглашение
подключения обычного профиля. Сид и пароль остаются в приложении.

После входа в панель создать **New profile invitation / Новое приглашение
профиля**, передать QR/приглашение в настройки нод приложения. Для каждого
нужного профиля создаётся отдельное одноразовое приглашение. Сам по себе вход
администратора не заменяет привязку профиля к очереди.

## Что проверять между хостингами

1. Прямой обмен сообщениями между аккаунтами старого и нового приложений.
2. Передача карточек/QR с адресом сети; добавление незнакомого сигналинга —
   после согласия пользователя. Оба приложения по умолчанию используют свой
   сигналинг; второй домен автоматически в список подключений не добавлен.
3. Обычный текст в офлайн-очередь через свою ноду и получение после появления
   собеседника. Для межнодового маршрута контактам нужны свежие подписанные
   объявления; произвольный Account ID не является глобальным поиском.
4. Для файлов и дополнительных устройств учитывать действующие ограничения:
   новый подписанный межнодовый мост относится к обычному тексту и не означает
   автоматическую репликацию любых данных между нодами.

Веб-хранилища разных доменов независимы. Обновление кода не переносит браузерный
аккаунт, переписку или права на другую ноду. При необходимости используйте
резервную копию/подключение устройств и привязку профиля по приглашению.

## Выполненные проверки

Обновление приложения с резервной копией и HTTPS/WSS-проверкой выполнено в
GitHub Actions. Установка и активация новой ноды также выполнены в GitHub.
Проверены отдельный node ID, HTTPS, подписанный WSS, запрет публичных служебных
путей и CORS для двух явно разрешённых origin. Посторонний origin отклоняется.
Оба сигналинга принимают разрешённый origin второго приложения, сохраняя свои
адреса по умолчанию. Это проверка инфраструктуры; пользовательские сценарии
доставки между реальными аккаунтами остаются ручной приёмкой.
