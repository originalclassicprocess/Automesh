## Подтверждённые проблемы

1. **Высокий риск доступности: падение сигналинга.** Некорректный JSON-тип
   поля в квитанции/запросе файла мог вызвать синхронный `TypeError`, выходящий
   из обработчика WebSocket. Это воспроизведено в отдельном процессе.
   Атакующему достаточно зарегистрировать собственную идентичность;
   ключ жертвы и привязка к её очереди для атаки на сигналинг не нужны.
   Исправлены строгие типы идентификаторов/подписей и внешняя граница обработки
   исключений: повреждённое сообщение не должно останавливать остальных клиентов.
   Это не доказательство чтения переписки, исполнения команд или кражи seed.

2. **Средний риск доступности: повреждённый JSON обходил байтовый лимит.**
   Число кадров ограничивалось, но невалидный JSON завершал обработку раньше
   учёта байтов. Добавлен лимит входных байтов до разбора и учёт повреждённых
   кадров в обычном бюджете. Отдельный потолок оставляет пропускную способность
   файлов; это не защита от любого распределённого DoS.

3. **Нет HSTS на работающем сайте.** В патч добавлен `max-age=31536000` для
   настроенного HTTPS-origin. Не доверяем `X-Forwarded-Proto`; HTTP-localhost
   не меняется. Без `includeSubDomains`/`preload`, чтобы не затронуть другие
   поддомены. HSTS не подписывает приложение и не защищает от взлома хостинга;
   без preload не решает первый небезопасный визит.
   [Описание HSTS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security).

4. **Высокий организационный риск: main и деплой не защищены отдельно.**
   GitHub API: `main.protected=false`, список environments пустой.
   API защиты ветки/rules возвращает 403: требуется GitHub Pro либо public.
   Репозиторий приватный; настройки не менялись. Ограничение workflow на main
   не запрещает человеку с правами записи изменить main или сам workflow.
   Хеши артефакта также не спасают, если атакующий меняет код и его контрольные суммы.
   [Доступность защиты веток](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## Порты и направления

Это назначение из кода/настроек, **не утверждение, что все эти порты сейчас открыты**.
При локальном замере слушателей на перечисленных TCP-портах не обнаружено.

| Порт/служба | Где и для кого | Защита/ограничение |
|---|---|---|
| 3003 TCP, HTTPS/WSS ноды | Выбранный LAN-IP и 127.0.0.1 | TLS, допустимые Host/Origin; API требует подписанный proof |
| 3004 TCP, управление | Только 127.0.0.1 | Bearer-токен, запрет browser Origin; в LAN не слушает |
| 3001 TCP, dev-сигналинг | По умолчанию 127.0.0.1 | Подписанная регистрация; отдельный запуск, не лишний listener установщика |
| 5173 TCP / 5174 TCP | Dev HTTP-loopback / отдельный HTTPS LAN-preview | Только разработка; не публичное production-развёртывание |
| 443 TCP, сайт/интернет-сигналинг | Хостинг automesh.space | HTTPS/WSS, CSP, signed registration, квоты соединений/кадров |
| WebRTC | Динамические сетевые порты, обычно UDP | ICE и защищённый транспорт; P2P может раскрыть IP собеседнику |

3002 — не текущий порт установленной ноды. Публичные/control-порты можно менять
в профессиональных настройках; таблица показывает значения по умолчанию.
Реальное правило `AutomeshNodeLAN-*`: включено, inbound TCP 3003,
Private, LocalAddress `192.168.0.140`, RemoteAddress `LocalSubnet`.
Это не разрешение доступа из интернета. Нода подключается к интернет-релею
**исходящим** WSS; проброс портов/UPnP для пересыльщика не нужен.
Правила роутера, прочие firewall-правила и IPv6-публикация отдельно не проверены.

## Что уже закрыто в проверенном коде

- API ноды: P-256 proof связан с nodeId, адресом, методом, путём и SHA-256
  точного тела. Challenge одноразовый, 30 секунд, не более 256 в памяти.
- Привязка: случайный одноразовый код, 10 минут, плюс proof владения аккаунтом.
  До 8 адресов. Чтение/ack только владельцу соответствующего ящика;
  запись — ему либо явно разрешённому отправителю.
- Тело API ограничено 192 КиБ, соединения/запросы/байты ограничены.
  Очереди/файлы имеют квоты и TTL; пути основаны на проверенных ID,
  файлы проверяются на symlink, запись атомарная. 20 МиБ на файл — политика.
- Seed и ключи расшифровки сообщений ноде не передаются. Нода сохраняет
  непрозрачные конверты/части файла. Подписанные квитанции проверяются прежде,
  чем удаляется ожидающая доставка; LAN-only учитывается маршрутизатором.
- Ключ пересыльщика, токен и пароль PFX защищены DPAPI CurrentUser,
  каталог — DACL текущего пользователя/SYSTEM. Ключ собственного CA удаляется
  после выпуска сертификата; нет постоянного ключа CA для подделки чужих сайтов.
- Production: CSP с nonce, запрет embedding/objects/base, nosniff/no-referrer,
  fixtures /dev не выдаются. SW кеширует только shell/ресурсы, проверяет
  совпадение версии и полноту перед активацией; не кеширует vault/очереди.
- CI: actions закреплены полными SHA, contents:read, checkout без сохранения
  credential, npm ci --ignore-scripts. Проверены хеш Node runtime, allowlist
  установочного payload, manifest файлов, SSH host key, transactional rollback.
  GitHub Actions не может автоматически одобрять PR.

## Остаточные риски и действия владельца

Приоритет: 2FA/passkey и резервные коды GitHub, регистратора/DNS и хостинга;
минимум допущенных аккаунтов/токенов. Для приватного репозитория рассмотреть Pro,
потом запрет force-push/delete/direct push и обязательные проверки/review main.
Настроить production Environment и перенести туда deploy secrets; доступность
required reviewers зависит от тарифа. Это требует отдельного согласования;
репозиторий ради этого не открывался, токены/SSH-ключи не ротировались.
[Рекомендации GitHub](https://docs.github.com/en/actions/reference/security/secure-use).

Злоумышленник под той же учётной записью Windows или администратор может
использовать DPAPI, файлы и работающий процесс. DPAPI защищает секреты на диске,
а не делает заражённый ПК безопасным. Нужны обновления ОС, защита устройства,
шифрование диска и отдельные учётные записи.
[Границы DPAPI](https://learn.microsoft.com/en-us/windows/win32/seccrypto/example-c-program-using-cryptprotectdata).

Установщик по-прежнему без цифровой подписи. Хеш на том же взломанном сайте
не является независимым подтверждением. Код signing для desktop — отдельный этап.
В браузере подменённый origin может заменить и JS, и SW, и проверку подписи:
нет обещания, что дополнительный JS-валидатор решит компрометацию хостинга.
CSP помогает против внедрения скриптов, но не является независимой подписью
изданного приложения. [CSP](https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/CSP).

LAN-участник может забить общий лимит/challenge pool/соединения; интернет-релей
может задерживать/отбрасывать пакеты, видеть адреса, время и объём. TLS не скрывает
IP. Нода не должна публиковаться через port forwarding, DMZ или туннель в интернет
в текущей итерации. Интернет-приём остаётся выключенным.

2FA владельца, права cPanel/SSH, DNS/регистратора, журнал компрометаций,
реальные WAN-порты и все расширения/приложения пользователя этим аудитом
не подтверждены. Known-vulnerability scan не доказывает отсутствие неизвестных ошибок.
