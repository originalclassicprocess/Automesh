## Что работает

- Один процесс: прежний сигналинг `/signal` и отдельный API очереди.
- TLS на выбранных частных IPv4 и loopback; нет слушателя `0.0.0.0`.
- До восьми изолированных аккаунтов на узле: локальный код на 10 минут + одноразовое доказательство
  владения ключом аккаунта. Account ID сам по себе не даёт управление.
- Очередь на диске: непрозрачные конверты, сохранение до ответа отправителю,
  повтор без дубликатов, подтверждение удаления владельцем и TTL.
- Только разрешённые владельцем отправители могут оставлять конверты;
  только получатель получает их и подтверждает получение. Отзыв запрещает новые
  загрузки, но не удаляет уже оставленные сообщения.
- Запускатель Windows: настройка сети/лимита, запуск/остановка, трей,
  опциональный автозапуск после входа в Windows, установка/удаление без npm.
- В браузере: Настройки → Связь → Серверы подключения → ПК-узел Automesh.
  Проверка, привязка, подключение сигналинга, статистика и разрешения.

## Как собрать

На Windows x64, в исходниках:

```powershell
npm ci
npm run node:build:windows
npm run build
```

Сборщик проверяет официальный SHA-256 Node.js 24, включает runtime и лицензии,
собирает единственный backend-файл и Windows-установщик IExpress.
Версия/контрольная сумма runtime закреплены в `nodes/adapters/windows/runtime.json`:
обновлять их вместе, не подставлять неподдерживаемую Node.js из системы.
Node.js/npm на пользовательском ПК не требуются.

Выход: `.release/home-node/Automesh-Node-Setup.exe`; копия и manifest находятся
в `static/downloads/`, поэтому следующая сборка клиента может отдавать файл.
Это генерируемые игнорируемые артефакты, не файлы в Git. Сборка клиента на Linux
сама не создаёт Windows-установщик. Если артефакт не включён в сборку/публикацию,
клиент явно сообщает об отсутствии скачивания.

Установщик **не подписан Authenticode**. Preview может вызывать SmartScreen.
Не отключать защиту Windows ради массовой установки; для публичного выпуска
нужны подпись, проверка установщика на чистой Windows и отдельный процесс обновлений.
Сборка сама ничего не устанавливает и не меняет сертификаты/автозапуск/брандмауэр.

## Пользовательская установка и привязка

1. Запустить установщик и нажать «Запустить» на вкладке «Обзор».
2. По умолчанию нода использует все активные сети Windows с профилем «Частная»;
   Wi-Fi и Ethernet обслуживаются одновременно одной очередью. Публичные сети
   не подключаются автоматически. Ручной выбор и лимиты — в параметрах.
3. Нода подготавливает TLS в фоне. Без домашнего интерфейса работает на localhost.
4. «Подключить приложение на этом ПК» предлагает явно подтвердить доверие своему
   CA, затем показывает QR и позволяет скопировать приглашение для localhost.
   Подписывающий ключ CA остаётся неэкспортируемым в хранилище текущего пользователя
   Windows; разрешены сертификаты для localhost, loopback и RFC1918, server auth,
   без вложенных CA. Это позволяет перевыпускать TLS при смене IP без нового корня
   доверия. Сид нигде не запрашивается. После старой версии нужен один перенос доверия.
5. Для телефона экспортировать **только публичный** CA `.cer`, передать по
   доверенному каналу и установить доверие средствами ОС. Браузер может отдельно
   запросить разрешение локальной сети. Никакого обхода TLS в клиенте нет.
6. «Разрешить LAN…» требует согласия UAC: открывается только TCP-порт узла,
   только Private и LocalSubnet, только node.exe из установленной программы.
   В автоматическом режиме правило переживает смену IP; в ручном ограничено
   выбранным интерфейсом/адресом. Public-профиль автоматически не меняется.
7. В клиенте вручную вставить HTTPS-адрес из окна узла; проверить и сверить ID узла,
   затем ввести локальный код и подтвердить привязку.
8. Включить «Использовать для офлайн-доставки» на обоих доверенных клиентах.
   Для второго аккаунта нажать в окне ПК-узла «Новый код» и привязать его отдельно.
9. Один раз соединить собеседников напрямую и открыть чат: клиенты передают
   подписанные описания узлов и отдельные запасы по 16 одноразовых открытых ключей.
   Новые партии выдаются при следующем прямом соединении; без запаса нет fallback.
10. Закрыть вкладку получателя, отправить текст. Через 10–20 секунд при доступном
    узле должно появиться «Сохранено на узле · ждём получения». Можно закрыть отправителя.
    После запуска получатель забирает сообщение; отправитель позже увидит «Доставлено».
    Порядок запуска клиентов больше не требует их одновременной работы.

ПК-узел должен оставаться включённым. LAN-узел доступен только внутри домашней
сети; вне её сообщения ожидают доступности узла или прямого соединения.
Спящий браузер не является фоновым получателем: доставка начинается при открытом
и разблокированном клиенте. Первый обмен ключами также требует прямой связи.

По умолчанию порты 3003 (TLS API + сигналинг), 3004 (контроль только loopback).
Адрес не зашит в клиент. В Windows автоматический режим проверяет домашние адреса
каждые 30 секунд и при изменении обновляет сертификат и перезапускает слушатели
после сохранения очереди. На этом ПК используйте `https://localhost:3003/`.
Удалённому телефону, у которого известен только старый IP, всё ещё нужен новый
адрес/QR или стабильное сетевое имя. Автоматическое обнаружение нод этим патчем
не реализовано; mDNS, DNS и сканирование сети не подменяются обещанием автопоиска.
Автоматическая проверка не открывает брандмауэр и не устанавливает доверие.

Установка: `%LOCALAPPDATA%\Programs\AutomeshNode`; данные и конфигурация:
`%LOCALAPPDATA%\AutomeshNode`. Закрытие окна скрывает его в трей;
«Остановить и выйти» сохраняет очередь и завершает процесс. Повторное открытие
ярлыка показывает уже открытое окно. Автозапуск — после входа пользователя, не системная служба
до входа. Спящий/выключенный ПК недоступен. Удаление программы сохраняет очередь
и конфигурацию; оставшееся локальное доверие/правило LAN явно описаны в диалоге.
Браузерная кнопка экстренного стирания НЕ удаляет данные отдельного ПК-узла.

## Протокол и границы безопасности

`automesh-node-v1`: публичный `/node/info` сообщает возможности и ID, но не
публикует владельца, разрешённых отправителей, код или содержимое очереди.
`POST /node/challenge` выдаёт nonce на 30 секунд, привязанный к Account ID,
HTTP-методу, пути и SHA-256 **точных байтов** следующего тела.
Подпись P-256 ECDSA/SHA-256 включает отдельный домен, ID узла и эти поля.
Nonce потребляется до асинхронной проверки и повторно не принимается.
Привязка Account ID к открытому ключу проверяется тем же общим кодом, что сигналинг.

Маршруты: `/node/pair`, `/node/join`, `/mailbox/put`, `/mailbox/list`, `/mailbox/ack`, `/mailbox/receipts`,
`/mailbox/status`, `/mailbox/grant`, `/mailbox/revoke`.
Подпись передаётся в `X-Automesh-Proof`, JSON в canonical base64url.
Тела до 192 КБ; непрозрачное содержимое конверта до 128 КБ; TTL до 7 дней.
По умолчанию до 1000 ожидающих конвертов, до 2000 записей с квитанциями,
до 100 ожидающих на отправителя, до 50 разрешённых отправителей.
Есть дополнительная общая/поотправительская квота байтов; переполнение отклоняется,
данные не вытесняются молча. ACK удаляет содержимое, но оставляет ограниченную
квитанцию до исходного TTL, чтобы повтор не воскресил сообщение.

Коммит — временный файл, fsync, атомарное переименование; на POSIX также fsync
каталога. После повреждения подтверждённых данных узел отказывается стартовать,
а не сбрасывает очередь. Ошибки не пишут сообщения, IP или аккаунты в логи.
Отдельный loopback-контроль защищён случайным токеном и отвергает любой browser
Origin. Публичный API проверяет Host/Origin, ограничивает запросы/байты/соединения.

Страница разрешает HTTPS в CSP `connect-src` для API самостоятельно выбранных
узлов, как WSS для сигналинга. CSP не умеет задавать диапазоны частных IP:
это расширяет разрешённые исходящие HTTPS-направления на уровне политики страницы.
Клиент узла отдельно принимает только явно введённые локальные HTTPS-адреса,
не сканирует сеть, не разрешает перенаправления и не передаёт cookies.
Остальные ограничения CSP (скрипты, объекты, worker и т. д.) не меняются;
доверие TLS, точный Origin и подписанные запросы остаются обязательными.

Узел НЕ может определить, действительно ли произвольные присланные байты являются
шифротекстом. Это задача клиентского протокола. HTTP-доказательство подтверждает
авторизованную загрузку на этот узел, но не заменяет E2EE-аутентификацию содержимого
у получателя. «Сохранено на узле» не означает «расшифровано» или «прочитано».
Оператор видит метаданные (включая разрешённые Account ID, размеры, сроки и
сетевые подключения). Узел не является анонимизатором.

## Одноразовые ключи и ограничения

Клиент хранит закрытые prekeys только внутри зашифрованной истории доверенного
аккаунта. Каждая партия предназначена одному отправителю. Перед загрузкой
отправитель сохраняет использованный ID ключа и точный шифротекст; повтор
отправляет те же байты. Повторное описание не возвращает использованные ключи.
Получатель проверяет подпись/Account ID/адресата/узел/TTL, расшифровывает HPKE,
затем одним сохранением записывает сообщение, удаляет ключ и сохраняет подписанную
квитанцию. Только после успешной записи подтверждает конверт узлу.
«Доставлено» устанавливается по подписи получателя, не по утверждению узла.

Это **не Signal Protocol / Double Ratchet** и не независимо аудированная реализация.
Одноразовость защищает перехваченные уже обработанные конверты от последующей
утечки оставшихся ключей, но не защищает историю на взломанном клиенте, ожидающие
конверты при утечке их ключей или старые резервные копии с удалёнными ключами.
JavaScript/IndexedDB не гарантируют физическое стирание следов и памяти.
Seed сам по себе не восстанавливает случайные prekeys; обычный зашифрованный
seed-файл их тоже НЕ содержит. Потеря браузерной истории теряет ожидающие конверты.
Доставка привязана к одному клиенту аккаунта; мультидевайс пока не реализован.
Блокировка останавливает опрос; недоверенная сессия не выдаёт и не получает prekeys.
Очистка истории удаляет локальные исходящие конверты, но не отзывает уже загруженные
на узел. Экстренное стирание браузера не стирает отдельный узел и данные собеседника.

## Проверки и оставшаяся работа

Автотесты: перезапуск, дедупликация/подмена ID, TTL/размер/квоты,
повреждённый диск, одноразовая подпись/изменение тела/пути, доступ владельца,
отзыв отправителя, чужой Origin/Host и прежний сигналинг.
Сквозной тест использует настоящий HTTP-auth API узла и браузерный контроллер:
обмен подписанными prekeys, остановка отправителя, перезапуск узла/состояния,
получение, удаление ключа и независимое получение подписанной квитанции.
Проверены подмена/чужой ключ/адресат, исчерпание prekeys, повтор описания,
точный повтор конверта, ложная квитанция и запрет загрузки без сохранения.

Следующие этапы:

- независимый аудит протокола и реализации;
- файлы, несколько устройств одного аккаунта, доступ узла из других сетей;
- проверить настоящую установку, сертификаты и автозапуск на чистой Windows;
- подпись установщика и безопасные обновления узла.

Не добавлены: NAT traversal/tunnel узла, системная служба, автоматические
обновления бинарника, облачные адаптеры, групповые чаты, хранение файлов и боты.
