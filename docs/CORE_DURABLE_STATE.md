# Долговечное состояние ядра — этап 0.1.4

Дата: 2026-10-04. Реализованы адаптер хранения и методы внутреннего API.
Опубликовано в 0.1.4 с отдельной проверкой `/diagnostics/core` на домене.
Это основа для будущих модулей: чат, почта и права ноды пока
используют прежние протоколы. HTTP API и профили этим этапом не добавлены.

## Границы

```text
Доверенный контроллер конкретного профиля
    ├── createCore: подпись, acceptOnce, authorizeStored, applyRevocation
    └── createBrowserCoreState: жизненный цикл и запрет записи после сброса
            └── createDurableCoreState: зашифрованное состояние, CAS-повторы
                    └── CoreRecordStore: атомарное хранение непрозрачной записи
                            └── IndexedDB (вне переносимого ядра)
```

Ядро не знает браузер, Svelte, HTTP или seed. Контроллер передаёт отдельный
неизвлекаемый AES-GCM-256 CryptoKey; браузерный адаптер разрешён только для
доверенной сессии. Для недоверенной сессии нет тихого перехода к защите в памяти:
долговечные операции недоступны, пока продукт не определит другой безопасный режим.

HKDF-SHA-256 получает ключ из 32-байтного материала идентичности, с отдельным
контекстом `Automesh core state key v1` и Account ID. Контекст не совпадает
с историей чатов. Временная копия входа стирается; seed не записывается.
Это не защищает состояние от обладателя seed или вредоносного кода клиента.

## Что хранится

Отдельная база `automesh-core-state-v1`, версия 1, store `profiles`.
Ключ записи — Account ID профиля. Открытая оболочка: schema, revision,
случайный 12-байтный IV, шифротекст AES-GCM. AAD связывает назначение,
Account ID и ревизию. На каждую попытку записи генерируется новый IV.

В шифротексте находятся отметки принятых операций, максимальное сохранённое
время, доверенные владельцы ресурсов, эпохи, последовательности обновлений,
сроки политики, отозванные grant ID и хеш последнего обновления.
Ни seed, ни текст сообщений не входят в это состояние. Адреса участников и
названия ресурсов зашифрованы; Account ID ключа записи, размер, число записей
и моменты обращения к диску не скрыты. Часть JS-данных живёт в памяти при
работе; надёжное физическое стирание памяти браузером не гарантируется.

## Атомарность и сбои

Чтение → расшифровка → изменение → шифрование выполняются вне транзакции.
Короткая read/write-транзакция проверяет прежнюю revision и записывает новую
только при совпадении. Две вкладки не могут успешно занять один claim.
Успех возвращается после commit, не после события put. Запись запрашивает
`durability: strict`; поддержка и реальная сохранность зависят от браузера/ОС.
Не поддерживающий эту операцию адаптер должен отказать, не обещать её выполнение.

После конфликта состояние перечитывается: максимум 16 попыток, затем отказ.
Ошибка диска, квота, повреждённая оболочка/шифротекст, неверный ключ или закрытие
не заменяют состояние пустым и не включают MemoryReplayStore.
Закрытие запрещает поздние результаты. Уже завершённый commit нельзя отменить:
claim может остаться занятым, даже если вызывающий код получил ошибку закрытия.

Лимиты защиты: 4096 действующих claims и 64 политики по умолчанию, конфигурация
до 10000/128; 1024 tombstones на политику; 2 MiB открытого состояния на профиль.
Переполнение даёт отказ, не вытеснение живых отметок. Просроченные claims удаляются.
Это **не лимиты сообщений чата или запаса одноразовых ключей доставки**.
Целая запись перешифровывается при изменении/проверке политики; для высоких
нагрузок нужен отдельный измеренный адаптер, а не обещание бесконечной ёмкости.

## Политика прав

1. Контроллер явно создаёт локальный anchor: известный issuer, получатель
   обновлений, точный resource, epoch и срок. Нельзя назначать владельца из
   неизвестного сетевого grant/revocation. Повторная инициализация запрещена.
2. `issueRevocation` подписывает обновление от самого issuer. `applyRevocation`
   проверяет подпись, автора, ожидаемый ресурс/получателя, audience и срок.
3. В body: issuer, recipient, resource, epoch, validUntil, sequence, revoked.
   Срок не дальше 7 дней, sequence положительный, grant ID уникальные UUID.
   Sequence монотонный для issuer/resource **также при смене epoch**.
4. Более старая эпоха/sequence отклоняется. Та же sequence допустима только
   при том же каноническом body: подпись и порядок ключей JSON не влияют на хеш.
   Одинаковая sequence с другим содержимым — конфликт.
5. В одной эпохе отзывы накапливаются, пропуск ID в следующем обновлении не
   восстанавливает право. Более высокая эпоха делает все прежние grants
   недействительными, после чего старые tombstones можно удалить.
6. Издатель должен отправлять **накопительный список отзывов текущей эпохи**:
   если sequence 2 придёт раньше 1, старое обновление не будет применено.
   Сам API подписывает переданный список и не ведёт за издателя журнал отзывов.
7. `authorizeStored` читает доверенную эпоху и после проверки подписи снова
   проверяет актуальные эпоху/отзыв/срок в хранилище. Нет политики, она устарела,
   диск недоступен или ответ неопределён — действие запрещено.

Контроллер отвечает за доставку обновлений. Freshness — сознательное окно
доверия: отключённый клиент не узнаёт новый отзыв мгновенно. Срок anchor не
продлевается автоматически. Подпись обновления обеспечивает аутентичность,
но **не шифрует сетевой body**, его приватная доставка требует отдельного E2EE.
Методы initialize/apply портов принадлежат доверенному контроллеру: их нельзя
раздавать плагинам как публичный способ менять политику.

## Ограничения гарантий

- Сохранённый максимум времени не даёт истекшим отметкам/политике ожить при
  откате системных часов после сохранённого наблюдения. Будущие неправильные
  часы могут преждевременно заблокировать работу; необходим явный recovery.
- Восстановление **всей старой базы**, удаление её или старый бэкап с ключом
  не выявляются одним AES-GCM/CAS. Для защиты от такого отката нужен внешний
  доверенный монотонный якорь. Seed восстанавливает ключ, но не журнал повторов.
- Claim и прикладной эффект не объединены: сбой между ними может потерять
  выполнение. Это at-most-once admission, **не exactly-once выполнение**.
- Проверка права и последующий внешний эффект также не одна транзакция;
  критичные операции требуют общей транзакции/повторной проверки у исполнителя.
- Старые версии приложения не знают эту базу. Не смешивать разные поколения
  клиента для операции, использующей новую долговечную защиту.
- XSS, подмена сборки, компрометация ОС/seed и гарантированная анонимность
  не решены. Это внутренние проверки, не независимый криптоаудит.

## Удаление и интеграция

Экстренное удаление интерфейса теперь очищает и эту базу всех профилей.
Сброс эпохи блокирует старые вкладки/поздние записи; закрытие также отключает
порты. Неудачная очистка показывается как частичная, остальные категории
всё равно очищаются. Удаление обычной истории чата не удаляет анти-replay журнал.
После явного полного удаления новая сессия начинается с пустым журналом:
прежнюю защиту от повторов обещать нельзя.

Для будущего модуля контроллер выводит ключ конкретного профиля, открывает
`createBrowserCoreState`, передаёт его replayStore/policyStore в `createCore`
и закрывает **оба** экземпляра при блокировке/смене профиля. API не владеет
переданными адаптерами и не уничтожает их вместо хозяина. При аварийном удалении
контроллер сначала останавливает операции и устанавливает эпоху сброса.

Следующий этап: контракт приватного реестра профилей и миграции. Главный корень
не должен становиться публичным issuer всех дочерних профилей; внешние права
подписываются соответствующим профилем. Требования — PROFILES_PRIVACY_CONTRACT.md.
