# LoRa: интеграция после первого аппаратного теста

План, не описание уже выпущенных функций. Серверы и релизы этим этапом не меняются.

1 ноября 2026: первая локальная интеграция реализована. Текущие возможности,
ограничения и порядок проверки описаны в [LORA_ACCOUNT_TEST.md](LORA_ACCOUNT_TEST.md).
Ниже сохранена исходная последовательность проектирования.

## Проверенная отправная точка

29 октября 2026 пользователь подтвердил двусторонний обмен двух Heltec V4 в
USB-стенде. Общий канал проверен без интернета. При отключении получателя
ложного подтверждения приложения не было. После исправления отрицательного
RSSI и приёма PKI/канал 0 подтверждён обмен при выбранном MyDevices. Это ручная
проверка пользователя, а не нагрузочное испытание или независимый аудит.

Стенд пока использует временные аккаунты, ключи и историю в памяти. Прикладной
ACK означает принятие этим стендом. Основной чат, его очередь и хранилище к радио
ещё не подключены.

## Границы реализации

- Транспорт доставки: радио с ограниченными датаграммами, задержками и потерями.
- Первая экосистема устройств: Meshtastic; особенности PKI, каналов и Phone API
  остаются внутри этого адаптера.
- Первый способ подключения к плате: USB/Web Serial.
- BLE — следующий адаптер связи приложения с той же платой, а не другой способ
  передачи сообщения по эфиру. Другие прошивки и прямые LoRa-модемы — отдельные
  будущие реализации; совпадение технологии LoRa само по себе не означает
  совместимость их протоколов, частот или модуляции.

Не создавать универсальный конструктор всех радиопротоколов заранее. Общая
граница должна описывать ограничения и результат доставки, а не копировать
Meshtastic channel/index/PKI во все слои приложения.

## 1. Основной аккаунт, хранение, подтверждения

1. Использовать текущую личность аккаунта для подписи радиоконтакта. Не создавать
   новую видимую личность для каждого транспорта; сид не передавать плате.
2. Сохранять ключи приёма, подписанные радиомаршруты и очередь в зашифрованном
   хранилище текущего профиля. Не оставлять модель одноразового стенда в основном
   приложении. Явно учитывать срок ключа и восстановление из резервной копии.
3. Для сообщения иметь единые логические ID, автора, адресата и содержимое,
   независимо от маршрута. Повтор по радио и поздний приём через IP не создают
   второй записи. Повторный ID с другим содержимым отвергается.
4. Радиоподпись, ключ адресата и аутентифицированное шифрование проверяются до
   записи в обычную историю. ACK отправляется только после успешной устойчивой
   записи, включая обработку повторов уже сохранённого сообщения.
5. Соблюдать блокировки контактов, согласие на переписку, границы профилей и
   существующие права устройств. Радиомаршрут не выдаёт административных прав.
6. Блокировка аккаунта закрывает USB-сеанс и освобождает радио-ключи из активного
   состояния. Перезапуск восстанавливает сохранённую очередь без объявления
   неподтверждённых сообщений доставленными.

Текущий `Transport`/`ChatService` использует надёжный упорядоченный поток и
12-секундное рукопожатие MAE. Не подавать в него необработанные радиопакеты и не
увеличивать общие таймауты интернет-чатов ради LoRa. Согласовать отдельный контракт
доставки медленных датаграмм с общей историей, очередью и подтверждениями. Это
отдельный путь доставки, а не вторая независимая база чатов.

## 2. Настройки и приглашения

Раздел «Связь и ноды → LoRa»:

- Подключить/отключить плату; состояние USB; модель, версия и номер радиомодуля.
- Прочитанные радиопараметры и выбор активного канала. Настройка платы остаётся
  отдельным явным действием; существующие частоты, мощность и ключи не менять молча.
- Радиоконтакт аккаунта: QR/копирование публичного подписанного маршрута и
  добавление маршрута существующему собеседнику.
- Приглашение в радиосеть с PSK показывать отдельно и только явным действием.
  Его нельзя подмешивать в обычную публичную карточку контакта.
- Режим «Автоматически, когда IP-пути недоступны» и ручной выбор LoRa в чате.
- Диагностика в раскрываемом блоке: USB, RX, PKI, очередь, код отказа прошивки;
  без текста переписки, приватных ключей и PSK.

LoRa в панели сетей открывает этот раздел. «Модуль подключён», «есть сохранённый
маршрут» и «получатель подтвердил сообщение» — разные состояния. Подключение USB
не означает, что собеседник онлайн. Недавний приём можно показывать с временем.

## 3. Выбор маршрута

Для первой версии — короткий обычный текст в существующих личных чатах:

1. Сохранять работающую прямую IP-доставку, включая локальный WebRTC/LAN без
   интернета. Один `navigator.onLine` не определяет доступность доставки.
2. Сохранять существующую очередь ноды и её подтверждённые состояния.
3. Пробовать радио, если подходящие IP-пути недоступны, LoRa разрешена,
   подключён модуль, есть действующий маршрут адресата и сообщение укладывается
   в ограничения. Ручной выбор радио позволяет проверить его независимо от IP.
4. После принятия сообщения нодой не запускать параллельную радиопередачу только
   из-за отсутствия немедленной квитанции. Дополнительный путь требует отдельной
   политики; единый ID и дедупликация обязательны при любой смене маршрута.
5. При появлении IP не начинать уже полученное сообщение заново. Для ещё не
   подтверждённого сохранять ID и содержимое; поздние квитанции обрабатывать
   идемпотентно. Ошибка одного пути не понижает подтверждение другого.
6. Ограничить очередь, размер текста, частоту попыток и повторы. Сохранять
   ограничения эфира прошивки. Не запускать бесконечное широковещательное
   обнаружение или перебор всех каналов.

Файлы, звонки, большие сообщения, исчезающие сообщения и операции, требующие
неподдерживаемой семантики, не превращать в обычный радиотекст. Показывать
конкретное ограничение и сохранять корректную очередь подходящего транспорта.

Статусы: очередь радио → передаём модулю → ждём подтверждения собеседника →
доставлено; отдельно таймаут, нет маршрута, USB отключён и отказ прошивки.
Радиоквитанция и постановка на модуль никогда не означают принятие приложением.

## 4. BLE и расширение оборудования

После устойчивой USB-интеграции добавить BLE под общим интерфейсом подключения
Meshtastic. Проверить отдельные GATT-границы, чтение очереди, уведомления,
размеры, разрыв, повторное подключение и владение сеансом; USB-кадры с заголовком
нельзя автоматически переносить в BLE-характеристики.

Доступность BLE/Web Serial зависит от браузера и платформы. Не обещать поддержку
всех телефонов через одну PWA до проверки целевых устройств. T114 проверить
после основного сценария на двух Heltec, без смешивания причин сбоев.

## Критерии первого интеграционного патча

- Те же аккаунты и обычная история на двух клиентах; сообщения остаются после
  перезапуска и имеют один ID при повторе через IP/радио.
- Подтверждение только после устойчивой записи; ошибка записи/расшифрования,
  чужая подпись, адрес или обычный канал не дают ACK.
- Реальный обмен без интернета; LAN при этом не объявляется недоступной лишь
  из-за отсутствия внешней сети.
- Отключение USB, поздняя квитанция, повтор, смена профиля, блокировка и
  восстановление не создают ложной доставки или передачи от другого аккаунта.
- Ограничения размеров и эфира видны пользователю; вложения и звонки не уходят
  в LoRa автоматически.
- Существующая доставка через прямые соединения и ноды проходит регрессионные
  проверки. Аппаратная проверка USB и проверка BLE фиксируются отдельно.
