# MeshAutonomy: границы ядра и приложения

Обновлено 4 октября 2026 года. Это описание работающего
кода, а не обещание поддержки будущих транспортов.

## Слои

```text
Svelte UI (+page.svelte, компоненты настроек/QR/резервной копии)
    │ действия пользователя и отображение состояния
    ▼
application/ — сценарии аккаунта, очередь отправки, порядок сохранений,
               сборка получаемых файлов, удаление старой телеметрии
    │
    ▼
chat/ — ChatService, SecureSessions, модель чатов, контакты/статусы,
        файловые кадры, правила режима устройства
    ├── message/ — конверт, подписываемые байты, общий кодек пакетов
    ├── identity/ + addressing/ — ключи подписи и Account ID
    └── Transport (контракт)
            ▼
       RoutedWebRTCTransport
          ├── WebRTCTransport: сигналинг → DataChannel
          └── DirectWebRTCTransport: QR → DataChannel

Браузерные адаптеры: vault/, chat/local-store.ts, service-worker.ts.
Внешний вспомогательный процесс: server/signaling.js.
```

## Обязанности

- **core/**: переносимая проверка аутентичности конвертов, подписанные объекты
  v1, ограниченные разрешения, порт защиты от повторов и внутренний API.
  Не создаёт серверы/транспорты, не хранит seed, не загружает плагины.
  Точные границы, состояние интеграции и ограничения — `CORE_V1.md`, API —
  `CORE_API.md`. Чат использует проверку конвертов; новые объекты/разрешения
  ещё не заменяют привязку нод и не включают будущие группы/профили.
- **identity/**: детерминированный ключ P-256, подпись и проверка. Не знает
  про UI, историю и конкретный транспорт.
- **addressing/**: Account ID v1, проверка формата, детерминированная аватарка.
  Не выбирает сети и не идентифицирует физического человека.
- **message/**: общий тип транспортного конверта, его бинарная упаковка,
  формат данных для подписи и проверка структуры. Кодек не зависит от WebRTC.
- **chat/**: вызов core для проверки подписи/получателя/привязки ключа к Account ID,
  экспериментальная E2EE-сессия, текст/служебные сообщения/файловые кадры.
  ChatService получает Transport обязательно через конструктор: скрытого
  создания WebRTC или альтернативной проверки открытого текста больше нет.
- **application/**: небольшие сценарные модули без Svelte. OutboxController
  получает отправителя, состояние и сохранение через функции; SerializedWrites
  упорядочивает записи; FileReceiver проверяет порядок и размер частей.
  accountFromMnemonic используется созданием, восстановлением и разблокировкой.
- **vault/** и **chat/local-store.ts**: браузерное хранение. Это адаптеры,
  а не обязательная часть независимого от платформы ядра. Компоненты Svelte
  в vault/ обслуживают UI резервной копии, не криптографический протокол.
- **transport/**: получение/доставка пакетов, установление и восстановление
  соединений. Конкретный транспорт не определяет правила контактов/прочтения
  или шифрования истории. RoutedWebRTCTransport выбирается в точке сборки
  приложения, не внутри ChatService.
- **server/signaling.js**: аутентифицированная регистрация, адресная
  подписка на присутствие, пересылка SDP/ICE. Переписку и файлы не хранит.

## Что намеренно осталось в странице

+page.svelte — точка сборки и реактивный UI: связывает события, показывает
настройки, выполняет блокировку/выход, управляет камерой/медиа и браузерным
хранилищем. Она ещё велика. Очередь текста, повторная криптографическая
деривация и упорядочивание сохранений вынесены; не следует считать весь
контроллер страницы уже полностью разделённым.

Дальнейшее разбиение: отдельные компоненты настроек и сценарий жизненного
цикла аккаунта, затем оркестрация файлов. Делать небольшими шагами с тестами
блокировки, смены режима и незавершённых записей, а не массовой заменой UI.

## Инварианты совместимости

1. Та же seed-фраза даёт тот же ключ и Account ID.
2. Формат подписанного конверта v2, MAE-сессий, частей файла, vault,
   зашифрованной истории и резервного файла не изменён.
3. Блокировка не удаляет историю. Недоверенная сессия не сохраняет новую
   историю на диск; поведение выхода остаётся прежним.
4. Статусы «Доставлено»/«Прочитано» не откатываются поздним завершением отправки.
5. Завершение старой отправки не меняет очередь новой сессии.
6. Логи аккаунтов, присутствия, сообщений, SDP/ICE не пишутся в консоль или
   localStorage. Старый ключ debugLogs удаляется при запуске UI на каждом origin.
   Если браузер запретил доступ, вход не блокируется, удаление повторится позже.

## Конфигурация и реальные ограничения

IP LAN задаётся при запуске, не зашит в клиент. Публичные сетевые параметры
приходят из mesh-runtime-config в HTML. STUN для интернет-маршрута вынесен в
client-config.ts: прежние Google-серверы остаются дефолтом, но их можно заменить
через MESH_RUNTIME_STUN_URLS (список через запятую) или отключить пустым значением.
LAN и прямой QR всегда используют только локальные кандидаты независимо от STUN.
Некорректная явная STUN-конфигурация отключает внешние обращения, не возвращает
Google молча. TURN и выдачи временных TURN-учётных данных пока нет.

Контракт текущего чата требует надёжной упорядоченной доставки для каждого
собеседника. LoRa/Bluetooth не заработают от одной реализации TypeScript-интерфейса:
понадобятся свой фрейминг, фрагментация/сборка, повторы и адаптация лимитов.
Значения их capabilities — резервные оценки, не реализованные функции.
Звонки не реализованы и в активных пресетах не объявляются поддержанными.
TTL — зарезервированное поле; multi-hop mesh и мультидевайс не реализованы.

Рабочие автотесты не заменяют независимый криптографический аудит.
Протокол приложения экспериментальный, не реализация Signal Protocol.

## ПК-узел (существующий отдельный протокол)

`server/node/` — отдельная точка сборки: переиспользует неизменённый
`server/signaling.js`, рядом подключает DiskMailbox, NodeState и проверку
одноразовых HTTP-доказательств. Непрозрачные конверты не проходят через SDP/ICE
и не меняют поведение ChatService/MAE. `src/lib/node/protocol.js` содержит только
общий формат доказательства/границы конверта; `client.ts` — браузерный HTTP-адаптер,
HomeNodePanel — управление привязкой/правами, не отправитель сообщений чата.

Windows-упаковка находится отдельно в `nodes/adapters/windows/` и
`scripts/build-home-node.mjs`. TLS-ключи создаются при настройке конкретного
узла, не включаются в артефакт. Seed не передаётся ни установщику, ни узлу.
Офлайн-доставка вынесена в `offline-controller.ts` с портами состояния/сохранения/
приёма/доставки и HTTP-адаптером. `offline-crypto.ts` использует стандартный HPKE,
отдельные prekeys, подписи описаний и квитанций. `offline-state.ts` валидирует
состояние внутри encrypted LocalChatData. ChatService только обменивается
описаниями по уже защищённому прямому каналу, не знает конкретного HTTP-узла.
Онлайн MAE не изменён; приватные ключи не уходят на узел.
Конкретные ограничения и дальнейшая интеграция — `docs/HOME_NODE.md`.
