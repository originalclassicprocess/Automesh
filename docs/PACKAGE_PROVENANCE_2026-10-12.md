# Проверка происхождения пакетов: GitHub, бесплатно

Этот этап добавляет GitHub artifact attestations, не Authenticode/SignPath
и не собственный сертификат подписи Linux. Корневой код приложения — MIT;
в поставку сайта включается LICENSE. Лицензии зависимостей и сторонних медиа
не заменяются MIT автоматически.

## Что именно подтверждается

При каждом выпуске Windows EXE и Linux tar.gz автоматически получают свой
SHA-256. В release workflow GitHub подписывает подтверждение происхождения
каждого готового файла. Проверяющий сверяет его с фактическими байтами файла,
репозиторием `originalclassicprocess/Automesh`, процессом
`.github/workflows/release.yml`, веткой `main`, GitHub OIDC issuer и hosted
runner. При известном исходном коммите закрепляются также source/signer digest.

Это подтверждает выпуск указанным процессом GitHub, а НЕ отсутствие уязвимостей,
добросовестность всех авторов, Windows publisher trust или воспроизводимость
бинарной сборки. Если злоумышленник получит управление репозиторием/процессом
сборки, он сможет выпустить вредоносную, но правильно аттестованную программу.
Нужны 2FA, защита main, ограничение владельцев/секретов и review изменений
сборки. Предыдущий `nodes/source-provenance.json` сверяет локальные исходники,
но не является криптографическим подтверждением пакета на GitHub.

Хеши и подтверждения вычисляются при сборке, вручную обновлять их не нужно.
Одинаковый номер версии не означает одинаковые байты: проверка всегда относится
к конкретному пакету. Замена EXE/tar.gz после аттестации требует нового
подтверждения. Подпись издателя позже также меняет EXE, поэтому её нужно делать
ДО GitHub-аттестации, а не после.

## Реализованный порядок

1. Два main-only job собирают Windows/Linux. OIDC/attestations write есть только
   в этих job, не в PR CI и не в job деплоя. Все Actions закреплены commit SHA.
2. `actions/attest` создаёт подтверждения конкретных готовых бинарных файлов.
3. `record-node-provenance.mjs` вызывает официальный `gh attestation verify`,
   закрепляет доверенную политику и только после успешной проверки добавляет
   ссылку на сборку и публичный `.sigstore.json` к описанию загрузки.
4. Site build повторно проверяет ОБА скачанных CI-артефакта, подтверждения,
   текущий исходный коммит и run ID. Ошибка блокирует публикацию, даже если
   `repeat_checks` выключен. `signed` остаётся false: это статус подписи издателя.
5. Карточки загрузок показывают ссылку и команду проверки, а не фальшивую галочку
   «проверено» по содержимому JSON. Браузер НЕ выполняет криптографическую
   проверку скачанного файла. У локальных пакетов нет подтверждения GitHub.

Локальная команда (нужны Node.js и официальный GitHub CLI):

```text
node scripts/verify-node-package.mjs --file ./Automesh-Node-Setup.exe
node scripts/verify-node-package.mjs --file ./Automesh-Node-Linux-x64.tar.gz
```

Опционально `--commit` закрепляет известный 40-hex коммит, `--sha256` — известный
64-hex хеш, `--bundle` — скачанное подтверждение. Все проверки обязательны при
указании параметра; ошибок/недоступности сети нельзя обходить «по хешу».
Команда не запускает и не распаковывает проверяемый файл, ограничивает размер
и время ожидания, не передаёт пути оболочке и не печатает сырые auth-диагностики.
После проверки запускать нужно именно проверенный файл, не другую копию.
Проверка не гарантирует, что сторонний процесс не подменит файл ПОСЛЕ неё.

## Что ещё необходимо для первого настоящего подтверждённого выпуска

- Бесплатные attestations доступны для ПУБЛИЧНЫХ репозиториев. Для private
  GitHub требует Enterprise Cloud; платный обход здесь не используется.
- Анонимные API-запросы к app и nodes repo сейчас вернули 404; это не доказывает
  отсутствия репозитория, но не подтверждает публичную доступность. Публичность
  этой работой не менялась. Перед открытием нужно проверить текущую историю
  репозитория на секреты; удаление секрета только из последнего коммита не
  удаляет его из истории. При утечке секрет необходимо отозвать/заменить.
- Нужно отдельно опубликовать изменения в main и запустить ручной release
  workflow. Локальные unit-тесты с mock CLI проверяют безопасную оркестрацию,
  но НЕ заменяют настоящий выпуск/проверку подписанного bundle на GitHub.
- Текущие локальные пакеты 0.4.1, сайт и production нода в этом этапе НЕ
  пересобирались/не деплоились и НЕ объявляются аттестованными.

Локально проверено: 137 файлов тестов / 842 теста PASS; Svelte/TypeScript
0 ошибок/предупреждений; production build PASS. Проверены включение корневой
MIT-лицензии в пакет сайта, проверка manifest, перенос и откат LICENSE вместе
с релизом. Старые релизы без MIT-поля остаются пригодны для отката. Отказы
верификатора и запись ссылок проверены с mock CLI; настоящее криптографическое
подтверждение на GitHub пока не создавалось. Локальный `gh` не установлен,
проверяющая команда в этом случае корректно завершилась с отказом, не успехом.

## Скачать из GitHub, не включая бинарники в приложение

Да, итоговая схема может хранить EXE/tar.gz и `.sigstore.json` в GitHub Releases
репозитория `AutomeshNodes`. Кнопка приложения указывает прямо на release asset:
скачивание начинается без открытия страницы GitHub. Не нужен proxy тяжёлых
файлов через сервер сайта, в приложении достаточно версии, описания и ссылок.
Для доступности всем пользователям репозиторий/релизы должны быть публичными;
токен владельца нельзя вставлять в приложение. Поведение загрузки/открытия
системного диалога зависит от браузера; web-приложение не может управлять им.

Это отдельный следующий шаг, ещё НЕ сделанный в этом изменении. Сейчас оба
пакета строит release workflow приложения и они скачиваются с сайта. Перенос
в `AutomeshNodes` требует отдельного процесса выпуска там и смены закреплённой
политики проверки на фактический repo/workflow сборки. Простая подмена URL
при старой проверке происхождения была бы неправильной. Релизы GitHub не
создавались, содержимое production сайта не удалялось.

## Самовыпущенный сертификат домашней ноды

Он решает ДРУГУЮ задачу: TLS подключения браузера/телефона к вашей ноде.
Его не нужно заменять ради GitHub-подтверждения и нельзя использовать его
закрытый ключ или master/identity key ноды для подписи установщиков.

Windows launcher создаёт отдельный локальный CA и TLS leaf (serverAuth),
срок — один год, SAN — localhost, 127.0.0.1 и выбранный частный IP. Закрытый
ключ CA после выпуска удаляется; TLS PFX и его пароль остаются для работы
ноды, секреты конфигурации защищаются DPAPI текущего пользователя. CA `.cer`
содержит только публичный сертификат. Доверять нужно только сертификату
СВОЕЙ ноды, с независимо проверенным происхождением/отпечатком. Доверие на
Windows не устанавливает его автоматически на телефоны.

При изменении адреса, истечении срока, утечке ключа или неверном SAN сертификат
нужно перевыпустить; после смены CA устройства должны доверять новой CA.
Постоянно обновлять сертификат при каждом выпуске приложения не нужно.
Нельзя отключать проверку TLS или предлагать всем установить произвольный CA
ради избавления от предупреждений. Для публичного подключения в обычных
браузерах нужен доверенный публичный HTTPS-сертификат; внутренний CA удобен
для контролируемой домашней сети/внутреннего backend с явным доверием клиентов.

Отдельно проверен публичный `node.automesh.space`: TLS-проверка hostname/цепочки
успешна, сертификат SSL.com, срок до 25 апреля 2027 года. Это НЕ проверка
сертификата конкретной домашней ноды на устройстве пользователя.
